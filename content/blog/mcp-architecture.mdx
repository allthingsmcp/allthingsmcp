An MCP architecture diagram becomes useful when it shows ownership. The host, client, and server do different jobs, and production systems add authorization, gateways, observability, and upstream services around those boundaries.

## Host: the application boundary

The host is the application a person uses. It coordinates model access, creates clients, and decides how capability requests appear in the product. Consent, workspace selection, approval interfaces, and cross-server policy belong here.

## Client: the protocol participant

The client translates host intent into MCP requests and interprets results. In the July 2026 revision, it does not establish a protocol-level session or complete an initialization handshake. Every request carries the metadata needed to interpret it.

Clients may call `server/discover` to learn server identity, protocol versions, and capabilities before sending other requests. Discovery is useful for compatibility checks, but ordinary requests remain self-contained.

## Server: a focused capability surface

The server exposes features for a domain. The three primary server primitives remain resources, prompts, and tools. A server can also support discovery, elicitation patterns, subscriptions, or negotiated extensions.

For Streamable HTTP, `Mcp-Method` and `Mcp-Name` headers let gateways route, meter, and authorize without parsing request bodies. List responses can include cache hints, which makes deterministic ordering operationally useful.

## Stateless protocol, stateful application

Removing `Mcp-Session-Id` does not prohibit application state. A server that needs continuity can mint an explicit handle and return it to the caller. Future requests pass that handle as visible application data rather than relying on hidden transport state.

This changes the production topology: compatible requests can land on any server instance behind a normal load balancer, while application state is managed explicitly.

## Server-to-client interaction becomes multi-round-trip

The 2026 revision replaces held-open server-initiated requests with Multi Round-Trip Requests. A server can return an `input_required` result containing input requests, and the client retries the original operation with corresponding responses.

## Draw trust boundaries separately

Protocol topology and trust topology are related but different. A remote MCP server may rely on an authorization server and downstream APIs. The access token for the MCP server must not be passed through to those APIs; the server needs credentials intended for each upstream service.

This guide deliberately keeps the surface small. A first server should prove the protocol boundary before it adds side effects or infrastructure.

## Choose one capability

Pick a deterministic read operation with a narrow input and result. Write down what the host should show a user before you write the server implementation.

## Create the server

Use a current SDK release that supports MCP `2026-07-28`. Give the server stable implementation metadata. For a local standard-input/output server, keep logs on standard error and reserve standard output for protocol messages.

## Add a read-only operation

Define one focused capability with an explicit schema. Treat names, descriptions, and annotations as part of the interface, but enforce input validation in the implementation.

## Inspect the request and result

Connect with an inspector or development host. Confirm the self-contained request metadata and the required `resultType` on the response. If the client uses discovery, verify the server reports the expected version and capabilities.

## Verify the boundary

Confirm invalid inputs return a useful error, logs contain no user payload by default, and no HTTP authorization behavior has been copied into the local stdio transport.

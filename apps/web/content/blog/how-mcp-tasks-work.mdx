Some `tools/call` requests take longer than a request should stay open: a large image batch, a CI run, a step that waits for a person to approve something. **Tasks is the MCP extension that lets an MCP server answer such a call immediately with a task handle, then report progress and the final result through short follow-up requests.**

This article builds a mental model of Tasks: the problem they solve, what a task is, and the messages that carry one from `tools/call` to its result. It uses a batch image resize as the running example, where an MCP server turns six images into eighteen thumbnails. If you want to implement the extension afterwards, [Build Your First MCP Task](/guides/build-mcp-tasks-with-sharp) walks through it on both an MCP server and an MCP client.

## Why a long tool call needs a task

An ordinary `tools/call` is one request and one response. The MCP client waits on that request until the MCP server returns the tool result. For a database lookup that takes milliseconds, that works. For a batch of eighteen image resizes, a CI run or a step that waits for a person, it breaks in three ways:

| Problem       | What happens with one long request                                   |
| ------------- | -------------------------------------------------------------------- |
| Timeouts      | Clients and intermediaries close requests that stay open too long.   |
| Lost results  | If the MCP client exits or the connection drops, the result is lost. |
| No visibility | The MCP client can't see progress or ask the work to stop.           |

**A task separates starting the work from collecting its result.** The MCP server answers the call right away with a task handle. The MCP client then checks on the task with short requests whenever it wants.

![Two sequence diagrams. Without Tasks, the MCP client sends tools/call and waits on one open request while the MCP server resizes 18 images; a timeout or disconnect leaves the result with nowhere to go. With Tasks, the MCP server returns a task handle immediately, the MCP client sends short tasks/get requests and sees "working, Created 6 of 18", and the last tasks/get returns completed with the final result.](/images/guides/mcp-tasks/why-tasks.svg)

## What a task is

A **task** is a record that the MCP server keeps for one `tools/call`. It has an unguessable ID, a status and a status message. When the task finishes, the record also holds the result. The MCP client never sees the work itself, only this record.

When the MCP server decides to run a call as a task, it returns a **task handle** in place of the tool result. Here is one, with annotations:

```jsonc
{
  "resultType": "task", // "this is a task handle, not the tool result"
  "taskId": "a1288bf1-305f-46ac-a49c-5c02a2828bc7", // keep this to check back
  "status": "working",
  "statusMessage": "Starting the image batch.", // human-readable progress
  "createdAt": "2026-10-27T10:41:57.590Z",
  "lastUpdatedAt": "2026-10-27T10:41:57.590Z",
  "ttlMs": 3600000, // the server may discard the task after one hour
  "pollIntervalMs": 500, // "please check no more than every 500 ms"
}
```

`ttlMs` and `pollIntervalMs` are values this example server chooses, not protocol defaults. A server may change either one during a task.

## Follow one task from call to result

The diagram traces the full exchange, including the worker and task store that this example MCP server uses internally. Those two are implementation choices, not protocol participants.

![Sequence diagram with three participants: MCP client, MCP server and task store. 1: the MCP client sends tools/call and its _meta declares Tasks support. 2: the MCP server saves a task with status working. 3: the server returns a task handle with resultType task and a taskId. 4: a worker resizes images in the background and updates the store. 5: in a loop every pollIntervalMs, the client sends tasks/get with the taskId and receives status working with a message such as "Created 6 of 18 thumbnails." 6: the client can exit or lose its connection; the task keeps running and a new connection polls the saved taskId without a second tools/call. 7: tasks/get returns status completed with a result in the same shape tools/call returns.](/images/guides/mcp-tasks/task-exchange.svg)

Four details in this flow matter when you write the code:

- **The server saves the task before it returns the handle** (messages 2–3). The specification requires this, so the MCP client's first `tasks/get` always finds the task.
- **The work runs outside the request** (message 4). The `tools/call` response is already sent, so a worker or job queue has to own the batch.
- **The task ID is how you resume** (message 6). Calling the tool again would start a second batch. Calling `tasks/get` with the saved ID follows the original one.
- **The final `tasks/get` carries the result** (message 7). Its `result` field holds exactly what an ordinary `tools/call` would have returned. There is no separate "fetch result" request.

The extension adds three methods to the `tools/call` you already know:

| Method         | The MCP client sends it to                                           |
| -------------- | -------------------------------------------------------------------- |
| `tools/call`   | Start the work. The response is a task handle or an ordinary result. |
| `tasks/get`    | Read the current status and, once finished, the result.              |
| `tasks/cancel` | Ask the MCP server to stop. The reply is an empty acknowledgement.   |
| `tasks/update` | Answer a request the task is waiting on, such as an approval.        |

Over Streamable HTTP, the MCP client also sets the `Mcp-Name` header to the `taskId` on every `tasks/*` request. A load balancer can use it to route polls to the server instance that holds the task.

## Read a task's status

Every task is a small state machine. Your MCP client decides what to do next by reading `status`:

![State diagram. A task starts in working after tools/call returns a task handle. It can move to input_required when it needs input and back to working after tasks/update; the image example never needs input. From working, a task ends in one of three terminal statuses that never change: completed when the result is ready, including when the tool result has isError true; failed for JSON-RPC errors only, not tool errors; and cancelled when tasks/cancel is honoured, although cancellation is cooperative and the task may still end as completed.](/images/guides/mcp-tasks/task-lifecycle.svg)

| Status           | What your MCP client does                                              |
| ---------------- | ---------------------------------------------------------------------- |
| `working`        | Wait `pollIntervalMs`, then call `tasks/get` again.                    |
| `input_required` | Show the requests in `inputRequests`, then reply with `tasks/update`.  |
| `completed`      | Read `result`. Check its `isError` too, because tool errors land here. |
| `failed`         | Read `error`, a JSON-RPC error that prevented a normal result.         |
| `cancelled`      | Stop waiting. Work already done may still exist on the server.         |

<Callout type="warning" title="A tool error is not a failed task">
  If the tool runs and reports a problem, such as an unreadable image, the task
  is `completed` and its result has `isError: true`. Only a protocol-level
  JSON-RPC error produces `failed`.
</Callout>

`input_required` is how a task pauses for approval or other input. The server places standard requests, such as an elicitation, in the `tasks/get` response. The MCP client answers them with `tasks/update` and goes back to polling. The image batch never needs input, so the example doesn't exercise that path.

## Who decides to create a task

Both sides opt in to the extension, but **the MCP server decides on each request whether to create a task**. The MCP client never asks for a task. It only states that it can handle one.

![Flowchart. The MCP client sends tools/call. If the request's _meta does not declare the Tasks extension, the server never returns a task: it returns an ordinary result, or error -32021 if it cannot do the work without one. If the request declares the extension, the MCP server decides per request: an ordinary CallToolResult for quick work, or a task handle with resultType task for long work. Your client must handle both shapes on every call. In the image example, a declaring client always receives a task handle.](/images/guides/mcp-tasks/who-decides.svg)

Each side declares support with the same extension identifier, `io.modelcontextprotocol/tasks`:

```jsonc
// MCP client: in every request's params._meta
"io.modelcontextprotocol/clientCapabilities": {
  "extensions": { "io.modelcontextprotocol/tasks": {} }
}

// MCP server: in its server/discover capabilities
"capabilities": {
  "tools": {},
  "extensions": { "io.modelcontextprotocol/tasks": {} }
}
```

Because the client declaration travels with each request, the server checks it every time. A server must never return a task to a request that didn't declare the extension. A server that can still do the work synchronously falls back to an ordinary result in that case. One that can't returns error `-32021`.

The practical consequence for client authors is that a call may come back in either shape. Check `resultType` on every response instead of assuming a task.

## When to reach for Tasks

| Good fit                                                   | Usually unnecessary                          |
| ---------------------------------------------------------- | -------------------------------------------- |
| Batch work: image or media processing, imports, migrations | Lookups and simple API calls                 |
| Pipelines and deployments that take minutes                | Work that reliably finishes in a few seconds |
| Approval steps that wait for a person (`input_required`)   | Streaming output back as it is generated     |
| Wrapping an API that already returns a job ID              |                                              |

The [official Tasks overview](https://modelcontextprotocol.io/extensions/tasks/overview) lists more use cases. The statuses, methods and rules in this article come from the [Tasks specification](https://tasks.extensions.modelcontextprotocol.io/specification/2026-07-28/tasks).

## What to remember

- The MCP server returns a **task handle with a `taskId`** in place of the tool result.
- An MCP client gets the result after reconnecting by calling **`tasks/get` with the saved ID**, never `tools/call` again.
- A tool error produces a **`completed`** task with `isError: true`. Only a JSON-RPC error produces `failed`.
- The server decides per request whether to create a task, so clients must handle both result shapes.

To see these messages in running code, follow [Build Your First MCP Task](/guides/build-mcp-tasks-with-sharp). You will build the MCP server, the MCP client, and then reconnect to and cancel a live task.

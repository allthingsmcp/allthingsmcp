A **resource** is data your server makes available at an address, called a URI. Where the model decides when to use a tool, the app decides when to read a resource: it might show the data to the user, or attach it to the conversation as context. Reading a resource never runs an action. It only returns data.

## 1. Add Supported cities

Select **Supported cities**. Note its URI, `weather://cities`, and its content type, `application/json`, then add it. You can compare it with **Weather API usage guide**, which lives at `weather://docs/usage` and returns Markdown.

## What a client sees

When a client lists your server's resources, Supported cities appears with its URI, its names and its content type:

```jsonc
{
  "uri": "weather://cities",
  "name": "supported_cities",
  "title": "Supported cities",
  "description": "A curated set of example cities.",
  "mimeType": "application/json",
}
```

To get the data, the client asks for that URI with `resources/read`. Your server answers with the contents:

```jsonc
"contents": [
  {
    "uri": "weather://cities",
    "mimeType": "application/json",
    "text": "{\"cities\":[\"Lagos\",\"London\",\"San Francisco\"], ...}",
  },
],
```

The URI is what makes a resource useful. It stays the same between requests, so an app can read it again later or link to it from elsewhere, without knowing anything about how your server produces the data.

<Callout title="Resource or tool?">
  Use a resource for data someone reads. Use a tool for an operation that takes
  arguments or does something. Keeping them apart helps a host decide what to
  show and what needs approval: reading a list of cities is harmless, while a
  tool might send a message or change data.
</Callout>

**Checkpoint:** your server offers `weather://cities`, and the **Code** tab shows a `server.registerResource` call with that URI.

Finish by handling an unsuccessful image operation, then change the input
without changing the MCP task workflow.

## 1. Try an invalid image

With the MCP server still running, use the supplied CLI wrapper:

```bash
pnpm run client run --images broken.png
```

After the task ID, the final lines include:

```text
completed: Batch returned a tool error.
Cannot process broken.png: Input buffer contains unsupported image format
```

The command exits with a nonzero status. The task says `completed` because the
tool returned a result describing its failure, with `isError: true`. That is
different from the `failed` state used for a JSON-RPC execution error. Your MCP
client must inspect the tool result as well as the task status.

Run it again with valid input:

```bash
pnpm run client run --images landscape.png
pnpm run verify --output
```

Expect three thumbnails and `Verified 3 WebP files against manifest.json.`
This is a new task; correcting the input does not rewrite the old attempt.

## 2. Validate the workflow with different input

Copy a JPEG or PNG into `fixtures/`, for example `my-photo.jpg`. Use the CLI's
`--images` option to process only that file, and `--widths` to request widths
**320 and 640**. Run the batch and inspect its manifest.

`src/client.ts` accepts comma-separated filenames and widths. Expect two
WebP outputs. A source smaller than the requested width stays smaller because
the resize function avoids enlargement. Use a new filename: `pnpm run fixtures`
overwrites the supplied sample names.

The [completed project's README](/downloads/mcp-tasks-thumbnails/completed.zip)
contains the command under “Try your own image.”

## 3. Verify the implementation

Stop terminal A with **Ctrl+C**, then run:

```bash
pnpm run typecheck
pnpm run test
```

The tests start their own local MCP server and should report no failures.

Your implementation now covers the core Tasks lifecycle:

- The MCP server persists a task before returning its handle and updates its state.
- The MCP client declares extension support and handles both response shapes.
- Polling retrieves the final result; reconnecting follows the same operation.
- Cancellation is checked by the worker, with the actual outcome read from the task.
- Tool errors are handled separately from task execution errors.

To apply this to report generation or another long-running tool, replace the
batch operation and its input/result schemas. The capability declarations,
task persistence and lifecycle handling serve the same roles.

## Beyond this local example

This MCP server uses a local file store and one worker process. It has no
authentication, distributed queue, automatic retries or job restart. Expired
records and partial outputs remain on disk. Those are application concerns to
address before adapting it for remote use.

The supplied HTTP adapter handles this example's JSON responses. It does not
implement approval prompts or subscription notifications. Explore the official
[input handling guide](https://tasks.extensions.modelcontextprotocol.io/typescript/client/input-and-recovery)
when a task needs user input, and the [Tasks overview](https://modelcontextprotocol.io/extensions/tasks/overview)
for other use cases.

The MCP server can now return a task. Your MCP client must declare that it knows
how to handle one, then distinguish a task handle from an ordinary result.
Keep the MCP server running in terminal A.

## 1. Write the tool caller

Replace `scripts/tasks-client.ts` with:

```typescript title="scripts/tasks-client.ts"
import { connect } from '../src/connection.ts';
import { sampleInput } from '../src/config.ts';
import { watchTask } from '../src/watch-task.ts';
import { z } from 'zod';

const capabilities = {
  extensions: { 'io.modelcontextprotocol/tasks': {} },
};
const connection = await connect(process.argv[2], capabilities);

try {
  const response = await connection.callTool(sampleInput);
  let result;
  if (response.resultType === 'task') {
    console.log(`Task ID: ${response.taskId}`);
    result = await watchTask(connection, response.taskId);
  } else {
    result = response;
  }
  if (result) {
    const output = z
      .object({
        content: z.array(
          z.object({ type: z.literal('text'), text: z.string() }),
        ),
        isError: z.boolean().optional(),
      })
      .parse(result);
    for (const item of output.content) {
      if (item.type === 'text') console.log(item.text);
    }
    if (output.isError) process.exitCode = 1;
  }
} finally {
  await connection.close();
}
```

The `capabilities` object opts this MCP client into Tasks. The supplied `connect()`
helper creates an SDK `Client`, connects over Streamable HTTP, and includes those
capabilities in every request's metadata. Open `src/connection.ts` to see where
`io.modelcontextprotocol/clientCapabilities` is attached.

The `resultType` branch is essential even when Tasks support is declared: the
MCP server may return either a task handle or an ordinary result. Both paths end
with a tool result, which this MCP client validates before printing.

`connect()`, `callTool()` on its returned object, and `watchTask()` are local
helpers. The connection code uses the extension's V2 schemas for the supplied
MCP server's JSON responses. For a broader application, the official
[Tasks client API](https://tasks.extensions.modelcontextprotocol.io/typescript/getting-started)
provides lifecycle helpers; its current V2 integration also requires a
[raw request adapter](https://tasks.extensions.modelcontextprotocol.io/typescript/adapters-and-schemas).

## 2. Follow the task to its result

Replace `src/watch-task.ts` with:

```typescript title="src/watch-task.ts"
import { setTimeout as delay } from 'node:timers/promises';
import { CallToolResultV2Schema } from '@modelcontextprotocol/ext-tasks/core/v2';
import type { Connection } from './connection.ts';

export async function watchTask(
  connection: Connection,
  taskId: string,
  log = console.log,
) {
  const deadline = Date.now() + 120_000;
  let previous = '';
  while (Date.now() < deadline) {
    const task = await connection.getTask(taskId);
    const message = `${task.status}: ${task.statusMessage ?? ''}`;
    if (message !== previous) log(message);
    previous = message;
    if (task.status === 'completed')
      return CallToolResultV2Schema.parse(task.result);
    if (task.status === 'cancelled') return undefined;
    if (task.status === 'failed') throw new Error(task.error.message);
    if (task.status === 'input_required')
      throw new Error(
        'This example does not handle requests for additional input.',
      );
    await delay(Math.max(100, task.pollIntervalMs ?? 500));
  }
  throw new Error(
    'Stopped waiting after two minutes; the server may still be working. Run the watch command again.',
  );
}
```

Each loop calls `tasks/get` through `connection.getTask()`, using the same ID,
and handles the statuses from the step 1 table:

| Status           | What `watchTask()` does                                                         |
| ---------------- | ------------------------------------------------------------------------------- |
| `working`        | Logs a changed message, waits `pollIntervalMs` (at least 100 ms), checks again. |
| `completed`      | Returns `task.result`, validated as a tool result.                              |
| `failed`         | Throws the JSON-RPC error message.                                              |
| `cancelled`      | Returns `undefined`, so the caller prints nothing.                              |
| `input_required` | Throws, because this image tool never asks for input.                           |

The two-minute deadline stops this MCP client from waiting forever. It does not
cancel image processing. This image tool never asks for input, so the example
reports `input_required` as unsupported. A general MCP client would handle the
requests and send answers via `tasks/update`.

In this extension version, **`tasks/get` includes the final result**. There is
no separate `tasks/result` request. See [task polling](https://tasks.extensions.modelcontextprotocol.io/specification/2026-07-28/tasks#task-polling).

## 3. Run your MCP client

In terminal B:

```bash
pnpm run tasks-client
pnpm run verify --output
```

The beginning and end should look like this. Your task ID and folder will differ;
polling may skip intermediate counts:

```text
Task ID: <task-id>
working: Starting the image batch.
working: Created 2 of 18 thumbnails.
...
completed: All thumbnails are ready.
Created 18 thumbnails.
Output: <your-project>/output/<batch-id>
Verified 18 WebP files against manifest.json.
```

Open the output folder and one WebP file. `manifest.json` lists each filename,
width, height and file size. The result points to local files shared by your MCP
server and MCP client; it does not transfer image files over MCP.

If the connection is refused, check that terminal A is running. For another
port, use `pnpm run tasks-client http://127.0.0.1:3002/mcp`. A `TODO` error means
one of this step's files still needs to be saved. Regenerate fixtures if an input
image is missing.

**Checkpoint:** your own MCP client declares Tasks support, receives a task ID,
checks its state and retrieves a result describing eighteen verified images.
The progress lines are stored task messages, not image-processing speed measurements.

Restart the MCP server from that folder if you switch projects.
